# v2026.7.1

Materializing a missing aggregate reads its stream once instead of twice (y bump: no API change).

## Why

`GetAsync<T>` on a registry miss read the whole stream twice: a prefetch outside the per-id
rebuild gate (to return early for ids that have no stream) and then an unconditional re-read
inside the gate, which was the snapshot actually replayed. On the largest streams that doubled
the deserialization cost of every materialization — an 82,367-event / 12 MB chat stream and a
13,413-event / 25.4 MB session stream are opened this way, and the prefetched list became garbage
as soon as the in-gate read returned.

## Content

- The stream is read **once, under the gate**. The prefetch is gone: a prefetch taken outside the
  gate could already be stale by the time the gate is acquired, and reusing it would replay a
  snapshot that predates two independent writers (a previous caller's rebuild that left nothing
  registered, and the shutdown side, which removes the registry entry *before* its draining loop
  flushes the terminal event). Reading under the gate makes "the replayed baseline cannot predate
  the gate" structural instead of a rule to remember.
- `_rebuildGates` is now a bounded LRU table (capacity 1024). A gate is dropped only when nobody
  is waiting on or holding it, so a dropped id always starts a fresh single-flight group — two
  groups for one id can never overlap. This deliberately differs from
  `InMemoryEventStore._locks`, which stays unbounded: its keys are aggregates that actually have
  streams (bounded by stored data), while the gate table is keyed by caller-supplied ids, including
  ids that do not exist.
- Unchanged: single-flight per id, the gate held through initialization, the registry re-check
  after the gate, failure cleanup, and "a registered but still initializing instance is not
  handed out".
- New regression pins: `RebuildLoadOnceTests` (a miss reads once; concurrent misses rebuild once
  and read once; the gate table stays bounded; a write after stop is included) plus the three
  race tests re-orchestrated around the single in-gate read (their assertions got stronger: one
  instance, one load, no stale resume).

## API delta

None — the public surface is identical to v2026.7.0 (`api/PicoActor*.public.txt` unchanged).
This is a **y** release and rides the next downstream lock refresh with no float-band edit.

## Wire / storage delta

None. Event streams and snapshot payloads are untouched.

## Breaking changes

None. `GetAsync` still returns `default` for ids with no stream; materialization is just cheaper
and the gates no longer accumulate per looked-up id.

## Limitations left open

- A rebuild without an applicable snapshot still replays the whole stream; snapshotting remains
  opt-in per actor (`SnapshotEveryNEvents` + `TakeSnapshot`/`RestoreSnapshot`).
- The gate capacity is a fixed constant (1024); it is not configurable.
- The store still has no cheap stream-version probe, so there is no way to reuse a read taken
  outside the gate even in the future; a probe would have to be a new, additive store capability.
