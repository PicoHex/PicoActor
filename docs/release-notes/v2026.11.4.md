# v2026.11.4

Patch release. **No API change** (`api/` baselines untouched). Fixes a stop-token race that 2026.11.3's CI
caught on `linux-arm64` / `net11.0`.

## The bug

`Actor.SignalStop()` closed the mailbox **before** cancelling the stop token, and the loop disposes its
`CancellationTokenSource` on exit. So the loop could observe the completed mailbox, exit and dispose the
CTS *before* the stopper reached `Cancel()`; that `Cancel()` then threw `ObjectDisposedException`, which
`SignalStop` swallows — leaving a **stopped actor whose `StopToken` never fires**.

Consequences: anything started with `StopToken` (a snapshot write, an in-flight async operation) waits
forever after `StopAsync` returned. It is a race, which is why it passed on `net10.0` and on Windows and
failed on `linux-arm64` with `net11.0`:

```
failed SnapshotWrite_ReceivesTheActorsStopToken
  Assert.That(token.IsCancellationRequested).IsTrue()  → found False
```

## The fix

- `SignalStop()` now **cancels first, then closes the mailbox**. Cancelling first makes the signal
  unlosable: `Cancel()` can no longer be pre-empted by a disposal it is racing with, and the mailbox
  close never depended on the CTS.
- The loop **no longer disposes** its `CancellationTokenSource`. Disposing there is what made the
  cancellation state lose-able, and a CTS with no timer holds no unmanaged resource — the collector owns
  it. `StopToken` therefore stays observable after the actor stops, which is its documented contract.
- The regression test (`SnapshotWrite_ReceivesTheActorsStopToken`) now runs the create → snapshot → stop
  → assert cycle **ten times**: one lucky pass proves nothing about a race, and the window opens on a
  loaded runner.

## Compatibility

No API, wire-format, naming or store-behaviour change. Everything in 2026.11.3 (the `net10.0` + `net11.0`
multi-targeting) is unchanged.
