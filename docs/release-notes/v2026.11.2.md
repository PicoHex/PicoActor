# v2026.11.2

Patch release (`y` bump): PicoJetson **2026.14.0**, and `SagaCompleted.Result` becomes **persistable** —
an `object?` member now dispatches on its runtime type, so a saga's terminal event carries a real result
instead of requiring `null`. No API of this repository changed, no wire format changed for anything
already written, and the one behaviour change is the serializer's own (see «Behaviour changes»).

## Why

v2026.11.0 bound the two saga terminal events into the store and had to document one shape it could not
carry: `SagaCompleted.Result` is `object?`, and PicoJetson 2026.13's generated writer emitted the member
with **no value** at all (`if (value.Result != null) { }`), so encoding a completion whose `Result` was
non-null threw in the serializer and wrote nothing, and the generated reader assigned `default!` to the
constructor parameter (`// unsupported ctor param type: any`). The workaround was a rule, not a fix:
**keep `Result` null**. A saga that computes an answer could not persist it.

PicoJetson 2026.14.0 closes that hole: a member declared `object?` is written by dispatching on the value's
**runtime** type, and read back by the same chain. Both defects are ones **this repository reported and
2026.14.0 fixed**: the `object?` member that was written as an empty block and read back as `default!`,
and the attribute pipeline's inability to emit a **positional record** (`[GenerateSerializer(typeof(T))]`
on a record with a primary constructor).

## Content

- **PicoJetson `2026.14.0`.** `Directory.Packages.props` floats PicoJetson to the `2026.14` band, so the
  packed `PicoActor.EventStore.Jsonl` nuspec depends on **`2026.14.0`** — it was `2026.13.3`. No other
  package's dependency changed. A consumer that pins PicoJetson below `2026.14.0` loses the behaviour
  below (its writer is the old one) but nothing else: the store's own API is untouched.
- **`SagaCompleted.Result` persists, with the fidelity a JSON number type can give.** What the store keeps
  is what the value was, within the any-value chain's forms:

  | `Result` written | Line on disk | Reads back as | Runtime type |
  |---|---|---|---|
  | `null` | `{"Result":null}` | `null` | — |
  | `"boom"` | `{"Result":"boom"}` | `"boom"` | `string` |
  | `true` | `{"Result":true}` | `true` | `bool` |
  | `42L` | `{"Result":42}` | `42` | `long` |
  | `7` (an `int`, or any integer kind) | `{"Result":7}` | `7` | `long` — **the documented widening** |
  | a runtime type the chain has no JSON form for (`new object()`, …) | — nothing is written — | — | `FormatException` **before** the first byte |

  The integer widening is the honest half of the bargain: JSON has one number type, 64-bit, so `7` written
  as an `int` comes back `7L`. Code that switched on the result's type must ask for `long` (or convert).
  The refusal is the other half: a value the any-value chain cannot put a JSON form to is **not** written
  as `ToString()` — the terminal batch throws `FormatException` whose message ends «has no JSON form in
  the any-value chain; write it with a concrete member type or a custom converter», and the store leaves
  **no file and no version** behind, exactly as it did before for every non-null value.
- **`Bnd15` flips from «loud failure» to «round-trip, and still loud for what cannot be represented».**
  The test that pinned the limitation (`Bnd15_NullResult_RoundTrips_NonNullFailsLoudly`) asserted two
  things: `Result = null` round-trips byte for byte, and `Result = "boom"` throws with no file on disk.
  The first half still holds; the second half is now the supported path, and the pin moves with it — the
  same test now round-trips `null`, `"boom"` and an integer (through the CONCRETE deserializer, reached as
  a method group, so this assembly still generates nothing and Bnd0's tripwire stays blind), and keeps a
  **loud failure with no stream and no version** for a runtime type the chain cannot represent. The name
  changes with the assertion; the obligation it guards does not.
- **Everything else is byte-identical.** A `Result = null` line is unchanged
  (`{"$type":"PicoActorSagaCompleted","Result":null}`), so a corpus of 2,403 null completions — every one
  in the reference corpus — reads, rewrites and enumerates exactly as before. No binding, tag, stream name
  or option gained a member; `api/PicoActor.EventStore.Jsonl.public.txt` is untouched.

## API delta

None. This is a dependency bump plus a serializer behaviour change; not a line of this repository's public
surface moved.

## Behaviour changes

- **A non-null `SagaCompleted.Result` is now a supported value** where v2026.11.x documented it as
  unsupported: `MarkComplete(result)` with a `null`, `string`, `bool` or integer result persists and
  replays. It reaches the store through an `object?` member the writer now dispatches on the runtime type,
  so the previous «the writer emits the member with no value» failure is gone.
- **A runtime type with no JSON form in the any-value chain is refused before any byte is written** — the
  same loud, file-less outcome as before, now for a narrower class of values and with a remedy in the
  message instead of a blanket «keep it null».
- **An integer `Result` reads back as `long`.** Documented, not a defect: one JSON number type, 64-bit.
  A consumer that needs the original kind converts at the boundary (`Convert.ToInt32`, a checked cast, or
  a typed field in a business event of its own base).

## Migration

① **Nothing to do for a null-result saga.** `Result = null` is byte-identical and stays the default advice
   for a saga whose answer belongs in a business event.

② **A saga that computes an answer can persist it now** — `MarkComplete("shipped")`, `MarkComplete(42)`.
   Read the value back through the concrete type; expect an integer to arrive as `long`.

③ **A saga that wants to persist a structure keeps it out of `Result`**: put it in a business event of
   your own `TEventBase` (as before) and complete with a `string`/`bool`/integer, or a `null`. A consumer
   type in `Result` is not silently coerced — the store does not fall back to `ToString()`, so it either
   has a form in the chain or it fails loudly and writes nothing.

## Limitations left open

- **The any-value chain is a value chain, not a polymorphic contract.** A `Result` is written by runtime
  dispatch over the forms the chain can express — `null`, `string`, `bool` and numbers are the ones this
  repository pins — and a consumer type with its own serializable shape is not automatically one of them;
  an unrepresentable one throws instead of being coerced. Typed payloads belong in a business event.
- **Integer kinds collapse into `long`.** A `short`, `byte` or `int` `Result` returns as `long`; the
  widening is documented above and not recoverable from the line alone.
- **Everything v2026.11.0 listed still holds** for the store itself: one codec, no aliasing, process-local
  bindings, one type/one tag, and the residual `Bnd19b` hole in the tag-clash guard.
