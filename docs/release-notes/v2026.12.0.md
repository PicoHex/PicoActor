# v2026.12.0

Minor release (`x` bump: two additive public members and one new optional interface). It makes a rebuild
of a long event stream cost the **tail**, not the file, and it makes the line counting behind every other
read 7–12× faster.

## Why

A production stream in the reference deployment — `SessionStarted-…jsonl`, **47.4 MB / 31,949 events** —
was rebuilt from scratch every activation:

```
before: full byte scan 103.6 ms (and 173.5 ms on a cold page cache) + replay 12.1 ms
```

The store could not address a version: `version` is the count of terminated non-blank **lines**, so finding
"the event after the snapshot" meant numbering the whole file. Two independent costs, two fixes.

## What ships

1. **Snapshots carry the byte offset they cover.** `ActorSnapshot` gains two init-only members,
   `StreamOffset` and `StreamLength` (`0` = not measured). The store records the position its append ended at
   (never `File.Length` — a second writer between the flush and the snapshot would make that describe a longer
   stream) and attaches it when the snapshot's version matches. `RebuildFromReaderAsync` then opens a cursor at
   that byte position (`IEventLogOffsetReader.OpenAtOffsetAsync`, a new optional capability) and derives the
   version from the events it reads → **one seek + the tail**.
2. **Line counting is vectorized.** `JsonlLines.Scan` finds `\n` with a vectorized search and decides
   "does this line carry content" with a vectorized `IndexOfAnyExcept(' ', '\t', '\r')`. Semantics are
   unchanged and **differentially tested**: a reference implementation of the previous byte loop is kept in
   the test project and compared positionally on adversarial corpora (CRLF, blank lines, `\r` alone, `\0`,
   BOM, U+2028/U+0085, lines straddling the 64 KiB buffer, >1 MB lines, torn tails) for every `fromVersion`.

## Measured (the same 47.4 MB / 31,949-event stream)

| | before | after |
|---|---|---|
| full scan (`GetVersionAsync`, real `FileStream`) | 103.6 – 173.5 ms | **14.1 ms** (3.4 GB/s, 7.4–12.3×) |
| rebuild with a fresh snapshot | 103.6 ms + replay | **one seek + the tail** (the tail read alone was 1.7 ms for the last 10%) |
| 50 k-line synthetic corpus (`MemoryStream`) | 5.13 – 5.99 ms | **0.59 – 1.13 ms** (5.2–8.6×) |

## Safety (the part that matters)

- An offset is **advisory**. It is believed only when it is `0` (empty stream) or when **all** of these hold:
  it is a line start (`file[offset-1] == '\n'`), `offset <= fileLength`, `StreamLength` also ends a line, and
  `fileLength >= StreamLength`. Anything else → **one warning, the calibration is dropped, the rebuild counts
  lines** (today's path). No input makes a rebuild throw.
- **A bounded witness covers the history the snapshot claims.** The header stores
  `fnv1a64(first min(64, offset) bytes) ^ fnv1a64(the min(4096, offset) bytes before the offset)` (O(1) at
  write and at read). A stream rewritten in place — fewer events, same bytes, offset still on a line boundary —
  changes that prefix and is **refused**: one warning, scan path, and the rebuild matches a full replay. This
  closed a real silent-wrong-state regression found in review (offset path `v5/value 555555` versus full replay
  `v3/value 333333`, with no warning).
- The witness is **a witness, not a proof**: a rewrite that preserves both windows *and* the geometry would pass.
  Anything stronger needs a checksum of the covered history, which is exactly the read the fast path exists to
  avoid.
- `IEventCursor.End` for a byte-position cursor reports `ulong.MaxValue` = "not measured" (the version is derived
  from the drain; a second observation would break the single-observation invariant). Nothing on the rebuild path
  reads `End` there — documented on the interface.

## Diagnostics

A snapshot written by a store that did **not** append the events it covers now logs one **Info** line:

```
Snapshot for aggregate '<id>' v<version> was written WITHOUT calibration: this store did not append that
version, so a rebuild will count the stream's lines instead of seeking to the snapshot. Write snapshots
through the store instance that appended the events.
```

The write still succeeds (losing acceleration is not a failure), but the degradation stops being silent —
which matters for a sealer or a wrapper that composes snapshots from its own path. A calibrated snapshot
(the normal case) logs nothing extra.

## Snapshot file format

Header grows **16 → 44 bytes**: `"PASJ" | u64 version | u32 payloadLength | u32 reserved | u64 streamLength |
u64 streamOffset | u64 coveredPrefixWitness`. It is **forward-only**: a 16-byte snapshot still decodes (with
`0/0`, i.e. "no calibration" → scan path), and an older PicoActor reading a new snapshot sees a payload length
that disagrees with the file, so it treats the file as "no snapshot" and replays the stream in full — the
documented degradation, since a snapshot is an accelerator.

## Compatibility

- Events, file naming, the `FileNameFormat` option, `EventTypeBindings` and the store's other public surfaces are
  unchanged. `InMemoryEventStore` is untouched and does not implement the new interface, so it keeps the scan
  path.
- Old snapshots keep working (they simply carry no offset); new snapshots make rebuilds fast.
- The `StreamOffset`/`StreamLength` members change `ActorSnapshot`'s record equality — noted because the type is
  public.
